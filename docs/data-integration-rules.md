# 대한민국 역명 통합 검색 — 데이터 통합 규칙 가이드

## 1. 문서 목적

이 문서는 데스크톱 프로그램 **대한민국 역명 통합 검색**에서 서로 다른 기관의 역·노선 데이터를 하나의 형식으로 통합하기 위한 기준을 정의한다.

- 1차 지원 범위: 서울·수도권
- 향후 범위: 부산, 대구, 광주, 대전, 일반철도 및 열차 종류별 정차역
- 기본 검색 단위: 역과 노선의 조합(`StationLine`)
- 원본 데이터는 수정하지 않고 정규화, 수동 예외, 최종 생성 데이터를 분리한다.

## 2. 디렉터리 규칙

```text
data/
├── raw/          # 제공기관에서 받은 원본. 직접 수정 금지
├── normalized/   # 공통 스키마로 변환한 데이터
├── overrides/    # 사람이 확인한 병합·분리·명칭·색상 예외
├── generated/    # 앱에서 읽는 최종 데이터
├── reference/    # 노선 색상 등 참고 데이터
└── metadata/     # 출처, 기준일, 수집일, 라이선스
```

데이터 처리는 다음 순서로 수행한다.

```text
원본 수집 → 출처별 변환 → 정규화 → 중복 후보 생성 → 자동 판정
→ 수동 예외 적용 → 검증 → 최종 데이터 및 검색 인덱스 생성
```

## 3. 핵심 엔터티

### Station

물리적 또는 서비스상 하나의 역을 나타낸다. 역명은 고유키로 사용하지 않는다.

필수 항목:

- `station_id`: 내부 고유 ID
- `official_name`: 공식 역명
- `normalized_name`: 검색·비교용 역명
- `initials`: 한글 초성
- `region_code`: 지역 코드
- `latitude`, `longitude`: 좌표
- `station_group_id`: 필요할 때 환승 거점을 묶는 ID
- `is_active`: 현재 운영 여부
- `opened_at`, `closed_at`: 유효기간

### Line

- `line_id`: 내부 고유 ID
- `official_name`: 공식 노선명
- `display_name`: UI 표시명
- `line_number`: 1, 2, 3 등 숫자 식별자
- `operator_code`: 운영기관
- `region_code`: 주된 지역
- `color_hex`: 노선 대표 색상
- `is_active`: 현재 운영 여부

### StationLine

역과 노선의 다대다 관계이며 검색 추천의 기본 표시 단위다.

- `station_id`
- `line_id`
- `source_station_code`
- `display_station_name`
- `sequence`
- `is_express_stop`
- `is_active`

같은 역이 여러 노선에 속하면 데이터베이스의 `Station`은 하나로 유지할 수 있지만 자동완성에서는 노선별 행으로 표시한다.

예:

```text
오금역  3호선
오금역  5호선
```

### TrainService와 StationService

KTX, SRT, ITX, 무궁화호는 노선이 아니라 열차 서비스 종류로 저장한다.

- `TrainService`: 열차 종류
- `StationService`: 해당 열차 종류가 정차하는 역

화면에서는 지역과 열차 종류를 같은 상위 선택 영역에 놓을 수 있지만 내부 코드는 `REGION`과 `TRAIN_SERVICE`로 구분한다.

## 4. 출처 추적

모든 정규화 레코드는 가능한 범위에서 다음 값을 보존한다.

- 제공기관
- 데이터셋명
- 원본 레코드 ID
- 원본 역 코드
- 원본 URL
- 데이터 기준일
- 수집일
- 가져오기 배치 ID
- 이용 조건 또는 라이선스

출처가 없는 레코드는 최종 데이터에 자동 반영하지 않고 검수 대상으로 출력한다.

## 5. 역명 정규화

공식 표기는 보존하고 비교·검색용 필드를 별도로 만든다.

정규화 순서:

1. 유니코드 NFC 정규화
2. 앞뒤 공백 제거
3. 연속 공백을 하나로 축소
4. 비교용 문자열에서는 공백 제거
5. 마지막의 `역` 접미사 제거
6. 괄호 안 부역명 분리
7. 가운데점과 유사 문장부호 표기 통일
8. 영문은 소문자로 변환
9. 한글 초성 문자열 생성

예:

| 공식 역명 | 정규화 역명 | 부역명 | 초성 |
|---|---|---|---|
| 무악재역 | 무악재 |  | ㅁㅇㅈ |
| 총신대입구(이수)역 | 총신대입구 | 이수 | ㅊㅅㄷㅇㄱ |
| 디지털미디어시티역 | 디지털미디어시티 |  | ㄷㅈㅌㅁㄷㅇㅅㅌ |

괄호 안 이름과 과거 명칭은 `StationAlias`에 저장하여 검색할 수 있게 한다. 공식 역명을 별칭으로 덮어쓰지 않는다.

## 6. 노선명 정규화

기관별로 `01호선`, `1호선`, `서울 1호선`, `수도권1호선`처럼 다른 표기가 들어올 수 있다.

- 원본 노선명은 보존한다.
- 내부 연결에는 `line_id`를 사용한다.
- `line_number`는 숫자 검색에 사용한다.
- 약칭과 과거 명칭은 `LineAlias`로 관리한다.
- 서울 2호선과 인천 2호선처럼 숫자가 같아도 별도 노선으로 유지한다.
- 숫자만 검색할 때는 현재 선택된 지역과 활성 노선 필터를 먼저 적용한다.

## 7. 중복역 및 환승역 판정

### 7.1 기본 원칙

정규화 역명은 중복 후보를 찾는 1차 기준이다. **역명이 같다는 이유만으로 즉시 병합하지 않는다.**

### 7.2 자동 병합 조건

다음 조건을 모두 만족할 때만 같은 `Station`으로 자동 병합한다.

1. 정규화 역명이 같다.
2. 같은 지역 또는 인접 행정구역이다.
3. 좌표가 500m 이내이거나 공식 환승 관계가 확인된다.
4. 서로 다른 역이라는 반대 증거가 없다.

자동 병합 결과에도 근거와 사용한 출처를 기록한다.

### 7.3 수동 검수 조건

다음 사례는 자동 병합하지 않고 검수 리포트에 기록한다.

- 역명은 같지만 시군구가 다름
- 역명은 같지만 좌표가 500m보다 멂
- 어느 한쪽 또는 양쪽 좌표가 없음
- 도시철도역과 일반철도역의 연결 관계가 불명확함
- 가까이 있지만 공식 환승 여부가 불명확함
- 부역명 또는 과거 명칭으로만 일치함
- 운영기관별 역명이 다르게 표기됨
- 하나의 역사인지 별개 역사인지 자료마다 다르게 표현됨

### 7.4 분리 유지 조건

- 실제 소재지가 다름
- 공식 환승 관계가 없음
- 다른 도시 또는 생활권에 위치함
- 폐역과 현재 운영 역이 별개의 시설임
- 수동 예외에서 `KEEP_SEPARATE`로 확정됨

### 7.5 수동 예외 파일

파일: `data/overrides/station-resolution.csv`

```csv
action,left_source_id,right_source_id,canonical_station_id,reason,verified_by,verified_at
MERGE,source-a-101,source-b-77,STN-000123,공식 환승역 확인,manual,2026-09-07
KEEP_SEPARATE,source-a-201,source-c-18,,동명이지만 다른 지역,manual,2026-09-07
```

허용 값:

- `MERGE`
- `KEEP_SEPARATE`
- `REVIEW`

사람의 판정은 생성 파일을 직접 고치는 대신 이 파일에 기록한다.

## 8. 검색 및 자동완성 규칙

### 8.1 네이버 지도 관찰 결과

2026-09-07 네이버 지도 수도권 지하철 출발역 자동완성을 관찰한 결과:

- `오금`은 `오금역 3호선`, `오금역 5호선` 두 행으로 표시됐다.
- `ㅇㄱ`는 안국역뿐 아니라 을지로입구역, 숙대입구역, 홍대입구역, 동대입구역, 압구정역, 월곡역처럼 초성열 내부에 `ㅇㄱ`가 연속으로 포함된 역도 추천했다.
- 같은 실제 역이라도 노선이 다르면 별도 행으로 표시됐다. 홍대입구역은 2호선과 공항철도가 각각 나타났다.
- 목록에는 역명과 노선명이 함께 표시됐다.
- 관찰한 목록은 최대 10개였으며, 단순 가나다순이나 초성 완전일치 순서만으로 정렬되지는 않았다.
- `3 ㅇㄱ`처럼 노선 번호와 초성을 공백으로 조합한 입력에는 추천 결과가 나타나지 않았다.

본 프로그램은 위 표시 패턴을 참고하되 `3 ㅇㄱ` 복합 검색은 확장 기능으로 지원한다.

### 8.2 초성 부분일치

초성 입력은 역명의 초성열 어느 위치에서든 **연속 부분 문자열**로 일치할 수 있다.

예:

```text
을지로입구 → ㅇㅈㄹㅇㄱ
검색어 ㅇㄱ → 일치
```

문자 순서만 같고 중간 문자가 떨어져 있는 비연속 부분 수열은 기본 일치로 취급하지 않는다.

### 8.3 다중 토큰 검색

공백으로 나눈 토큰은 기본적으로 AND 조건으로 결합한다.

```text
3 ㅇㄱ
```

- `3`: 현재 지역의 노선 번호 3
- `ㅇㄱ`: 역명 초성열의 연속 부분일치
- 두 조건을 모두 만족하는 `StationLine`만 반환

따라서 3호선에 속하면서 초성열에 `ㅇㄱ`가 들어간 역들이 추천 대상이 된다.

`3`을 무조건 3호선으로 해석하지 말고 현재 범위에서 숫자 노선이 존재하는지 확인한다. 역명 자체에 숫자가 포함되는 데이터가 생길 경우 노선 토큰과 일반 텍스트 토큰의 판정 근거를 기록한다.

### 8.4 일반 부분일치

- `오금` → 오금역
- `악재` → 무악재역
- `입구` → 이름에 입구가 연속으로 포함된 역
- 마지막 `역`은 있어도 없어도 동일하게 검색

### 8.5 추천 행의 단위

추천 결과는 `Station` 단위가 아니라 `StationLine` 단위로 표시한다.

각 행에는 최소한 다음을 표시한다.

- 역명
- 노선명
- 노선 색상 또는 배지
- 필요할 때 지역명

동명이역을 구분해야 할 때는 행정구역 또는 운영기관을 보조 정보로 표시한다.

### 8.6 정렬 기준

권장 기본 점수:

1. 역명 완전일치
2. 역명 시작일치
3. 역명 일반 부분일치
4. 초성열 완전일치
5. 초성열 시작일치
6. 초성열 연속 부분일치
7. 별칭 일치

(오타 유사일치는 2026-09-19 사용자 요청으로 제거했다 — 짧은 노선 별칭이 다른 노선명과 뒤섞이는 오탐이 더 컸다.)

필터 일치는 점수 가산이 아니라 필수 조건으로 먼저 적용한다. 동점이면 다음 순서로 정렬한다.

1. 선택한 운행 범위와 노선에 일치
2. 현재 운영 중
3. 완전일치 위치가 앞쪽임
4. 공식 데이터 우선순위
5. 역명 가나다순
6. 노선 정렬 순서

인기도 정보가 확보되지 않은 초기 버전에서는 임의의 인기도 점수를 만들지 않는다.

## 9. 노선 색상

참고 URL:

`https://ko.wikipedia.org/wiki/틀:한국_철도_노선색`

파일: `data/reference/rail-line-colors.csv`

```csv
scope_code,operator_code,line_code,line_name,color_hex,text_color_hex,source_name,source_url,source_revision,verified_at,notes
```

규칙:

- 색상은 `#RRGGBB` 대문자로 저장한다.
- 노선 연결에는 표시명이 아닌 `line_code`를 사용한다.
- 출처 URL, 확인일, 가능하면 원본 리비전 ID를 저장한다.
- 추출하지 못한 값은 임의 색으로 채우지 않는다.
- 같은 `line_code`에 다른 색이 있으면 검수 오류로 처리한다.
- 운영기관 공식 자료가 있으면 공식 자료를 우선하며 override 근거를 기록한다.
- 배경색 명암을 계산해 `text_color_hex`에 `#000000` 또는 `#FFFFFF`를 저장한다.
- 색만으로 노선을 구분하지 않고 노선명을 항상 함께 표시한다.
- 앱 실행 중 외부 페이지를 호출하지 않고 검증된 CSV를 로컬에서 읽는다.
- 출처의 라이선스와 표시 조건을 README 및 배포 문서에 기록한다.

## 10. 출처 우선순위

충돌 시 기본 우선순위:

1. 해당 노선 운영기관의 최신 공식 자료
2. 국가철도공단 또는 국토교통부 자료
3. 지방자치단체 공공데이터
4. 기타 공공기관 자료
5. 위키백과 등 공개 참고자료
6. 사람이 입력한 미검증 자료

더 낮은 순위의 자료라도 기준일이 훨씬 최신이거나 상위 자료의 오류가 공식적으로 확인되면 수동 override로 선택할 수 있다. 선택 사유와 확인자를 기록한다.

## 11. 검증 규칙

최종 데이터 생성 전에 다음을 검사한다.

- 내부 ID 중복
- 같은 출처의 원본 ID 중복
- 존재하지 않는 역·노선 참조
- 좌표 범위 오류
- 노선상 순서 중복
- 출처 누락
- 필수 검색 문자열 누락
- 같은 이름의 분리된 역 후보
- 자동 병합 불가 후보
- 수동 예외가 참조하는 원본 ID 누락
- 잘못된 HEX 색상
- 노선 코드별 색상 충돌
- 폐역 또는 비활성 노선이 기본 검색 결과에 노출됨

오류는 빌드를 실패시키고, 사람이 확인할 항목은 별도의 CSV 리포트로 출력한다.

## 12. 데이터 갱신 절차

1. 새 원본을 날짜별 폴더에 저장한다.
2. 출처 URL, 기준일, 수집일을 기록한다.
3. 출처별 변환기를 실행한다.
4. 이전 정규화 결과와 변경점을 비교한다.
5. 중복 후보 및 삭제·추가 역 리포트를 검토한다.
6. 기존 수동 override가 계속 유효한지 검사한다.
7. 자동 테스트와 데이터 검증을 실행한다.
8. 검수 승인 후 `generated` 데이터를 교체한다.
9. 변경 로그에 추가·변경·폐역 및 출처를 기록한다.

## 13. 알려진 한계

- 역명만으로는 모든 동명이역과 환승역을 정확히 판정할 수 없다.
- 서로 다른 운영기관의 좌표와 역 코드가 일치하지 않을 수 있다.
- 환승역의 물리적 경계와 서비스상 동일 역의 기준이 다를 수 있다.
- 노선색 참고자료는 공식 운영기관 값과 다르거나 변경될 수 있다.
- 네이버 지도 자동완성 관찰은 UI 설계 참고이며 해당 서비스의 내부 검색 알고리즘 전체를 의미하지 않는다.
- 열차 정차역과 운행계통은 시기별로 변경될 수 있으므로 유효기간 관리가 필요하다.
